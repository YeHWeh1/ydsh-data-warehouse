# 从"跑通了"到"算对了"——第 3 周项目周记

**闫洪伟　云仓五号　2026-11-09**

---

## 一、这周我做了什么

第 3 周的任务，用一句话概括：把前两周洗干净的数据，变成能看、能算、能预测、还能"开口说话"的东西。

我主要负责三块。第一块是数仓的汇总层和应用层——在已有的 DWD 明细层之上，按天、周、月、品类、门店、渠道这些维度把订单金额、订单量、用户数汇总起来，再落到面向具体业务的 ADS 表上。最后算出 GMV、订单量、客单价、活跃用户数、复购率、品类占比这几个核心指标。第二块是 NL2SQL，让系统能听懂"销量最高的前 5 个品类"这种人话，自己生成 SQL 去查。第三块是收尾的打包和文档。

数据规模不大，但"做对"和"跑通"之间的距离，比我想的远得多。

## 二、第一个坑：指标口径不统一，等于没算

刚开始我直接上手写建表语句，写完跑通就以为完事了。直到有一天对比第 2 周的结果，发现同一个 GMV，两个地方算出来不一样。

问题出在分母。客单价 = GMV ÷ 订单量，但"订单量"到底算全部 15,000 单，还是只算金额有效的 14,696 单？两种算法差了几十块钱，单看数字都合理，放一起就是"数出多门"。

部署手册里其实早就写了——"先写《指标定义文档》统一口径"，我当时跳过了这一步。补写文档的时候才发现，需要定清楚的不只是客单价：金额只统计 `is_valid_amount = 1` 的订单、品类 GMV 要按明细金额占比分摊、周起点不能用 `weekofyear()`（2024-12-30 会被算成 2025 年第 1 周，跨年周会裂成两段）、年同比根本没有 2023 年数据所以不可用……

这份文档最后成了本周所有代码的唯一口径来源。**先定义，再实现**，这个顺序颠倒不得。

## 三、第二个坑：模型精度不错，但它在骗我

这是本周最有意思的一件事。

预测建模部分，我按任务书要求从 Hive 读出每日 GMV，做了趋势分解、移动平均，然后用 scikit-learn 训练模型预测未来 7 天。滚动回测跑下来，线性回归 MAPE 12.42%，比"昨天=今天"的朴素基线（19.88%）好了不少。我当时的想法是：可以交了。

直到我把 7 天的预测值打印出来——96,687、98,069、100,350、102,742……**几乎是一条平线**。极差只有 3,091 元。

但历史数据里，周一和周二的平均 GMV 差了 8,000 多元，星期效应非常明显。模型把这个结构性规律完全抹掉了，它实际在做的事是"输出一个接近均值的数"。

我加了个诊断：比较预测序列和历史序列的变异系数。结果是预测 CV 0.95%，历史 CV 18.46%，**差了 19 倍**。这下实锤了——模型不是在预测，是在偷懒。

原因是递归预测的机制问题：预测第 1 天用真实的滞后值，但预测第 2 天时，`lag1` 用的已经是第 1 天的**预测值**了。一路递推下去，输入的方差不断衰减，输出自然收敛到均值。

解决办法是换一条路线：先把序列按星期因子去季节化，在平稳化后的序列上做回归，预测完再乘回星期因子。这样星期结构就不会被递归过程吃掉。改进后预测 CV 提升到 3.05%，极差从 3,091 元变成 8,069 元，**而且 MAPE 同时从 12.42% 降到了 11.54%**——结构保真和精度提升是同时发生的，不是取舍关系。

这件事让我印象很深。**MAPE 12.42% 是个"正确"的数字，但它掩盖了"模型已经失效"这个事实。** 如果我只盯着指标，交上去的就是一份精度尚可、但业务方拿去排产毫无指导意义的报告。

后来我还在报告里专门写了一节，把这个陷阱和诊断方法记下来了。

## 四、第三个坑：AI 给的答案，得自己验

这周大量用了 AI 辅助。它确实快——SQL 模板、PowerShell 脚本、图表代码这些"结构确定、细节繁琐"的活，效率是人的好几倍。

但踩的坑也不少，而且都很典型：

**中文列名。** 我让 AI 生成品类周趋势宽表，它写了 `as cat_运动户外`。Hive 直接报 `ParseException: character '运' not supported here`。AI 知道"SQL 可以用中文别名"（很多数据库确实可以），但不知道**这个版本**的 Hive 不行。改成拼音缩写加中文注释才解决。

**品类名靠常识编。** 它按印象写了"数码电器""食品饮料""家居家装"，而实际数据里是"数码家电""食品生鲜""家居生活"。结果三个品类列全是 0。教训很直白：**涉及真实取值的字符串，必须先 `select distinct` 查一遍**。这个错第 2 周已经犯过一次，这周又犯了。

**XGBoost 反而不如线性回归。** AI 倾向推荐 XGBoost，理由是"非线性表达能力强"。实测 MAPE 15.39%，比线性回归的 12.43% 差得多。样本只有 352 天，树模型容易记住噪声。**复杂不等于更好**，这话说起来简单，真到选模型的时候还是容易被"高级感"带偏。

**最隐蔽的一个：** AI 在离线模板里写"当日处于星期 2024-01-20 的固定低位"——把日期直接填进了"星期"的位置。这个错被两层机制抓到：数字校验发现正文里没有对应的星期数值，人工通读发现语义不通。

所以我在 AI 洞察那块加了个数字回溯校验：把生成文本里的所有数值抽出来，逐个和事实包比对（容差 2%），通过率低于 80% 就标红。实测下来异常归因和经营摘要的通过率都是 100%。

但我也清楚，**数字对不等于结论对**。AI 说"周一 GMV 低是因为周末效应消退"，这是因果推断，数据里根本没有证据支持，只是相关性。报告里我统一改成了"可能原因"，并明确列出"数据中无法验证"的部分——促销、竞品、天气、系统故障。

## 五、Git 协同：终于有真实记录了

这周还有个插曲。之前我写的 Git 协同记录里，"PR #1~#5""Issue #12~#19"这些编号其实是编的——当时觉得"应该有"，就按套路写了。后来一查 GitHub API，仓库的 PR 数、Issue 数、分支数全是 0。

这比没有记录更糟。老师点开仓库一看，PR 是 0，文档里却写着 5 个，那不就是造假吗？

我把那份文档改成了诚实版：保留真实的线下评审记录（5 次评审、9 个问题，内容都是真的），删掉所有虚构编号，并如实写明"PR 0 条、Issue 0 条、Tag 0 个"。

后来真的走了一次完整的 PR 流程。组员从 Fork 发起 PR，提了 `CHANGES_REQUESTED`，要求补充异常金额判定规则、对齐品类差异倍数。我实测后发现他给的两个数字（14,398 单、14.21 倍）都对不上——我用他说的"10 万业务阈值"重算了一遍，结果和 IQR 口径完全一致，都是 14,696 单；品类差异倍数实测是 11.42 倍。

于是补了文档、附了可复现的校验 SQL，在 PR 上留了带实测数据的回复。**这一次是真的有据可查了。**

顺带说，那个"14,398 vs 14,696"的差异，最后确认不是阈值口径造成的，而是两边数据源/去重逻辑不同。这种跨仓库的口径对齐，比单方面写完就交要有价值得多。

## 六、这周的收获

技术上，最大的收获是学会了**怀疑自己的评估指标**。MAPE 好看不代表模型有用，复购率 100% 不代表用户粘性强（1,000 个用户分摊 15,000 单，人均 15 单，所有人必然复购，这个指标在本数据集上区分度就是 0）。指标算对了，不等于指标有信息量。

流程上，是"先定口径再写代码"这个顺序。这周开头跳过这一步，后面返工的时间远超写文档的时间。

协作上，是"AI 给方向，实测给结论"。这周至少四个 AI 方案被实测否定（中文列名、品类名、XGBoost、正则误杀），每一条都是跑出来才知道的。AI 是很好的执行者，但不是合格的质量守门人。

## 七、下周打算

第 4 周要做可视化和部署。这周做的 ADS 表和看板算是打了个底，但现在的看板还是个静态 HTML，交互和数据刷新都不够。另外指标口径文档还得继续维护——每加一个指标就要补一条定义，否则又会回到"数出多门"的老路。

最后想说一句：这周最值钱的东西，不是那 11.54% 的 MAPE，也不是 8/8 通过的 NL2SQL 测试，而是那个"预测是平线"的发现。**如果没发现它，我们交上去的是一份看起来完整、实际上没有信息量的报告。** 数据工作最大的风险从来不是写不出代码，而是写出了看起来对的错误结论。
