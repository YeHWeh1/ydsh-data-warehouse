## 三、团队评审记录（线下）

> 说明：本周的代码评审在团队线下进行（每周例会 + 代码走查），
> 尚未在 GitHub 上建立远程 PR 记录。以下为实际发生的评审意见与对应修改。

### 评审 1：预测建模的回测方式

**提出人**：柴传兴（数据分析师）
**问题**：回测用的是什么切分方式？如果是随机 KFold，时间序列会数据泄露。

**修改**：改为滚动回测（walk-forward）——最后 28 天，第 t 天只用 `[0, t)` 的数据训练，逐日推进。
并在《预测建模分析报告》第三节写明"为什么不能用随机 KFold"。

**验证**：`py/forecast.py` 的 `rolling_backtest()` 实现，实测 28 个预测点。

---

### 评审 2：预测值是否退化

**提出人**：刘祎炫（项目经理）
**问题**：MAPE 12.42% 看起来不错，但预测值是不是太平了？业务方拿去没法用。

**修改**：补 `diagnose_flatness()`，用变异系数对比历史与预测的波动幅度。
实测纯递归预测 CV 0.95% vs 历史 18.46%，确认是平线。
新增季节调整路线，CV 提升到 3.05%，MAPE 降到 11.54%。

**验证**：`reports/data/forecast_summary.json` 中 `diagnosis` 与 `diagnosis_plain_recursive` 两组数据。

> **这条评审意见直接改变了本周的技术方案**，是本周最重要的技术发现。

---

### 评审 3：NL2SQL 的安全性

**提出人**：闫洪伟（数据工程师）
**问题**：大模型生成的 SQL 直接执行，如果有人问"删除所有订单"会怎样？

**修改**：加三层防护——
1. `FORBIDDEN` 正则拦截 DML/DDL；
2. 表名白名单（21 张表），不在白名单直接拒绝；
3. 明细查询自动追加 `LIMIT 200`。

并补了降级逻辑：模型生成的 SQL 不合法时回落到规则引擎，同时记录被拒的 SQL 供审计。

**验证**：`py/nl2sql.py` 的 `validate_sql()`，实测 8 条用例全部通过。

---

### 评审 4：正则表达式的误杀风险

**提出人**：柴传兴（数据分析师）
**问题**：正则 `\b(set|add)\b` 会不会误杀？`offset` 里含 `set`。

**修改**：改用 `(?<![\w.])(...)(?![\w.])` 边界匹配，避免 `offset` / `dataset` 这类误判。

**验证**：8 条测试用例全部通过，`group by` 不再被误判。

---

### 评审 5：客单价口径

**提出人**：刘祎炫（项目经理）
**问题**：客单价的分母是总订单量还是有效订单量？和第 2 周对得上吗？

**修改**：统一为**有效订单量**，与第 2 周 `ads_kpi_overview` 对齐。

**验证**：第 3 周 AOV 2,519.59 元，与第 2 周完全一致；品类 Top1 占比 14.88% 也完全一致。
口径变更记入《指标定义文档》第九节。

## 六、团队约定

1. **提交前**：`git status` 确认没有临时文件（`_temp/`、日志）带进去。
2. **一个提交只做一件事**，提交信息用 `feat/fix/docs/refactor/chore` 前缀。
3. **不提交**：模拟数据（`模拟数据/`、`*.csv`）、个人材料（`resume/`、`个人文件/`）、
   密钥与配置（`.env`、`*.key`、`*.pem`）、压缩包（`*.zip`）。
4. **推送前**：按 `AGENTS.md` 要求汇总变更内容并确认，不自动推送。
5. **冲突解决**：保留双方语义，不是简单选一边；解决后必须跑一次完整验证。
